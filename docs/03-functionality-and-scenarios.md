# 按应用场景回顾小车的功能模块

> 场景：**无网/弱网环境下的免手语音指挥配送小车**（医院病房 / 养老院 / 仓库）
> 目的：把"我们做了一辆车"翻译成"我们解决了场景里的哪些问题、还差什么"。

---

## 一、场景的任务闭环（一句话）

> 护士双手端着药盘（**腾不出手**）→ 说「小车过来」→ 小车从走廊自主走到病房门口
> → 说「跟我走」→ 跟到床边 → 卸货 → 说「回去」→ 返回护士站。

三条硬约束贯穿全程：**免手操作**（人不能去碰屏幕）、**没有网络**（病房区不可靠且录音不能上云）、
**安全攸关**（走廊有病人和老人）。

---

## 二、按场景需求重新组织现有模块

（不是按代码文件分组，而是按"场景要什么"分组）

| # | 场景需要什么 | 为什么场景需要 | 对应功能模块 | 状态 |
|---|---|---|---|---|
| 1 | **免手唤醒** | 护士双手不空，不能去按键 | 离线唤醒词「你好小车」 | ✅ |
| 2 | **免手指挥** | 同上 | 7 条本地口令（前进/后退/左右转/停下/开关灯） | ✅ |
| 3 | **连续作业不重复唤醒** | 边走边下指令，中途不该再喊唤醒词 | 命令窗随车而动（车在动 = 窗口有效） | ✅ |
| 4 | **随时能停** | 走廊突然出现病人 | 急停 5 同义词、不受任何门禁、可中止转向 | ✅ |
| 5 | **停得住** | 不能碰到人 | 超声波物理急停（18cm 触发，70cm 起先减速） | ✅ |
| 6 | **不会撞上去** | 前方有人/物 | 前方有障碍时拒绝执行"前进" + RGB 灯示警 | ✅ |
| 7 | **能精确转向** | 进病房门、绕床 | IMU 航向闭环 90° 转向（含惯性精修） | ✅ |
| 8 | **走得动、走得稳** | 地面摩擦、驱动板抽风 | I²C 100kHz + 200ms 心跳重发 + 驱动看门狗 | ✅ |
| 9 | **状态可见** | 护士要知道"它听懂了吗" | 屏幕"听到: xx" + 拒识提示 + RGB 灯 | ✅ |
| 10 | **走到指定位置** | **护士不会走过去叫它** | 定位与导航（里程计 + 航向） | ❌ **缺** |
| 11 | **边说边走带路** | 边走边引导到床边 | 跟随控制（超声波跟人） | ❌ 缺 |
| 12 | **承载货物** | 配送药品/器械 | 托盘/货架 | ❌ 缺（硬件改造） |
| 13 | **到达有提示** | 护士抬头就能确认 | 提示音 + 灯闪 | ⚠️ 只有屏幕 |
| 14 | **多点任务** | "去 3 号床"≠"往前走两米" | 站点/路径记忆 | ❌ 缺 |
| 15 | **长时间可靠** | 无人值守 | 电池监测（**已有读数，未使用**）| ⚠️ 有数据没用 |
| 16 | **在无网环境里"呼车"** | 护士在房间里，车在走廊 | 本地无线呼叫（ESP-NOW / 蓝牙） | ❌ **缺（场景特有）** |

## 三、诚实的定位：现在是什么，缺什么

| | 现在的小车 | 场景需要的设备 |
|---|---|---|
| 交互粒度 | **逐条指令**（"前进""左转""停下"） | **任务级**（"过来""去 3 号床""回去"） |
| 人的参与 | 人必须**跟着车**、边走边指挥 | 人只说目标，车自己完成 |
| 定位 | 只知道转了 90°（相对航向） | 知道自己在走廊的哪个位置 |
| 呼叫 | 人走到车旁边说唤醒词 | 远距离呼车 |

> **一句话：现在是一台"语音遥控车"，场景要的是一台"能自己完成配送的设备"。
> 差的正好是"从指令到任务"这一层。**（这也正是历届获奖作品的形态差异所在。）

## 四、补齐路线（按性价比排序）

### P0 — 半天内可完成，直接提升演示完成度

| 任务 | 怎么做 | 价值 |
|---|---|---|
| **到达提示音 + 灯闪** | 复用板载音频/屏幕 + 超声波 RGB | 任务闭环的"反馈感"，演示很直观 |
| **电量与自检上报** | 电机板已有电池电压读数，接进屏幕/日志 | 场景里"无人值守"的必备项 |
| **屏幕显示任务状态** | 待机 / 已唤醒 / 执行中 / 前方受阻 / 到达 | 让评委一眼看懂车在想什么 |

### P1 — 1~2 天，决定场景可信度（关键）

| 任务 | 怎么做 | 备注 |
|---|---|---|
| **"小车过来"** | 航点导航：编码器双轮里程算位移 + IMU 航向闭环 | **官方 `car_control.c` 里已有 Kalman + 双轮里程 + 航向控制，可直接移植**；我们已把 IMU 跑通，转向前提具备 |
| **"跟我走"** | 用**同一个超声波**测距跟随人（保持在 40~60cm） | 我们已有超声波驱动，是导航的副产物 |
| **"回去"** | 同上，航点反向执行 | |
| **无网呼车（ESP-NOW）** | 护士端一个小 ESP32 按钮；按下发 ESP-NOW 广播 → 小车应答并出发 | **ESP-NOW 不需要路由器**，正好适配"无网"场景；这是场景特有的设计点，答辩很出彩 |

### P2 — 需要动手改造

| 任务 | 说明 |
|---|---|
| 载物托盘 | 3D 打印 / 亚克力板，装在小车顶部（与"场景形态"有关，评委会看实物） |
| 多点站点（"去 3 号床"） | 在 P1 的航点基础上加站点表 |

## 五、往场景靠的时候，哪些该强调、哪些该弱化

| 模块 | 场景里的定位 | 处理 |
|---|---|---|
| 免手唤醒 / 口令 / 命令窗 | **核心需求** | 重点讲 |
| 四层安全设计（意图→现实→执行→兜底） | **核心创新** | 重点讲，这是与历届作品拉开差距的地方 |
| 90° 闭环转向 + 惯性修正 | 精确作业的基础 | 讲，并讲"日志说 90 度眼睛看到 150 度"那条方法论 |
| 可复现评测台 + 判决算法 | **方法论贡献** | 重点讲（这是我们的差异化护城河） |
| 车头灯（开灯/关灯） | 场景里意义不大 | 降为"同一套判决逻辑可迁移到其他动作"的例证 |
| I²C 100kHz / 心跳 / 看门狗 | 看起来像"修 bug"，其实是**可靠性设计** | 包装成"面向不可靠执行链路的容错控制"|

## 六、这张表可以直接变成答辩的第 3 页

> **左边一列写"场景需要什么"，右边一列写"我们用什么模块满足它"，
> 最后一列诚实标注"已实现 / 待补"。**
>
> 这样评委看到的是一个**需求驱动的系统设计**，而不是"我们攒了一堆功能"。
> 而且"待补"那几项恰好就是下一步的工作计划 —— 显得有规划，不做作。
