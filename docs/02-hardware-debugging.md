# 硬件调试记录：语音识别正常但小车不动

> 现象：对小智说「你好小车」→「前进」，**屏幕正常显示"听到: 前进"，但小车一动不动**。
> 这篇记录整个定位过程 —— 有日志证据、有对照实验、有可复现的结论。

---

## 一、先解决"没有证据"的问题

排查一开始就撞上一个坑：日志里明明打了

```
I (26960) motor: wheel speeds (M3/M4) = [22, 22]  i2c=OK
I (26970) CustomWakeWord: ACTION: forward (until 'stop')
```

看起来电机指令下发成功了。但翻开源码 `motor.c` 才发现：

```c
esp_err_t motor_set_wheel_speeds(int8_t left, int8_t right) {
    int8_t speed[4] = {0, 0, left, right};
    ESP_LOGI(TAG, "wheel speeds (M3/M4) = [%d, %d]", left, right);   // ← 写在 I2C 之前
    return motor_write_speeds(speed);                                // ← 返回值没人检查
}
```

**这行日志是在写 I²C 之前打的，而且写入结果被直接丢弃。**
也就是说：哪怕驱动板根本没收到指令，日志也一模一样。这就是"看起来正常但车不动"
一直找不到原因的根本原因。

**第一步改动**：把结果和电池电压一起打出来，再加一条开机自检 + 动作后编码器核对：

```
I (8261) motor: === MOTOR SELF-TEST (t+8s) ===
I (8261) motor:   i2c write addr=0x34 : ESP_OK
I (8261) motor:   battery = 8059 mV          ← 电池正常(2S 满电约 8.4V)
I (8261) motor:   encoder totals = ...       ← 编码器能读
```

同时给每个动作加了"1.2 秒后核对编码器位移"：

```
W (28160) motor: motion check: wheels DID NOT turn (dL=0 dR=0)
```

**从这一刻起，"车不动"有了直接证据：指令下去了、驱动板 ACK 了、但轮子一个脉冲都没走。**

## 二、证据链（每一步都排除一种可能）

| 步骤 | 做法 | 结果 | 排除/确认 |
|---|---|---|---|
| 1 | 读电池电压 | **8105 mV**，电量充足 | 排除电池没电 |
| 2 | 查 I²C 写入返回 | **ESP_OK**（ACK 正常） | 排除驱动板失联 |
| 3 | 逐通道驱动 M1~M4 | M1/M2 编码器不动、**M3/M4 正常** | 确认驱动轮在 M3/M4（与官方例程一致） |
| 4 | 带载电压监测（每 100ms 采一次，取最低值） | 失败时 **8067~8101 mV，几乎不掉压** | **排除"电池带不动电机"** —— 没掉压说明驱动板压根没输出 |
| 5 | 速度扫描 22/25/30/35/40/50 | 22、30、40、50 不动；25、35 正常 | 一度以为是"某些速度值不行" |
| 6 | **同一速度重复 3 次** | 22：失败失败成功；25：失败失败失败；30：失败失败 —— **14 次只有 5 次成功（36%）** | **推翻"速度问题"，确认是间歇性故障** |
| 7 | 四种 `MOTOR_TYPE` 各测 3 次 | 成功率都是 2/3 左右 | 排除电机类型参数问题 |
| 8 | 看编码器读数的具体数值 | 出现 **dL=47330025 dR=77639896**、**51965041 / 85628510** 这种几千万的乱码；电池读数也时不时返回 **0 mV** | **关键线索：I²C 通信本身不可靠** |

第 8 步是转折点。电机不会转出 4700 万脉冲 —— 那是**读回来的数据是垃圾**。
连同"电池读回 0"和"指令写进去不生效"，三件事指向同一个原因：**这条 I²C 链路不可靠。**

排查物理侧之后（电机线插紧、电池断电重启、驱动板自检正常），回到软件：

**`motor_init()` 里 I²C 速率写的是 400 kHz。**

改成驱动板原生支持的 **100 kHz** 后：

```
I (12261) motor: === MOTOR PROBE START (idle battery=8084 mV) ===
I (14261) motor:   [第1次] dL=  4396 dR=  4399 ... OK
I (17461) motor:   [第2次] dL=  5149 dR=  5150 ... OK
I (20661) motor:   [第3次] dL=  5150 dR=  5150 ... OK
I (23861) motor:   [第4次] dL=  4897 dR=  4900 ... OK
I (27061) motor:   [第5次] dL=  5149 dR=  5150 ... OK
I (30261) motor:   [第6次] dL=  4397 dR=  4398 ... OK
I (33461) motor:   [第7次] dL=  5151 dR=  5151 ... OK
I (36661) motor:   [第8次] dL=  4898 dR=  4898 ... OK
>>> I2C@100kHz 驱动成功率 8/8
```

**8/8 全成功**，而且转速也稳定了（目标 25 → 2500 脉冲/秒，实测 2200~2575/秒）。

### 根因

> **驱动板（0x34，带 STM32 协处理器的那块模块）在这条线路上跑不了 400 kHz。**
> 表现为：指令时灵时不灵、编码器读回乱码、电池读回 0。
> 降到 100 kHz 后完全稳定。

驱动板本身支持标准模式(100kHz)，而我们的速度指令 200ms 才发一次，
对带宽毫无要求 —— **降速零代价，收益是彻底稳定。**

## 三、软件侧的两道加固

即使链路修好了，考虑到这条线路是排线+插针（接触电阻、电机 EMI 都可能干扰），
又加了两层保护：

### 1. 速度指令心跳（每 200ms 重发）

```c
static void motor_heartbeat_task(void *arg) {
    while (1) {
        vTaskDelay(pdMS_TO_TICKS(200));
        if (s_target_l != 0 || s_target_r != 0) motor_apply_speeds();
    }
}
```

单次下发的成功率实测只有 20%~90%（时好时坏），改成心跳重发后：
**双轮 25 → 4/4，双轮 35 → 3/3。**

### 2. 驱动看门狗（有目标却不动就重新初始化驱动板）

```c
if (moved == 0) {
    stalls++;
    if (stalls >= 2) {              // 连续约 1 秒不动才动手, 避免读数抖动误触发
        int8_t zero[4] = {0,0,0,0};
        motor_write_speeds(zero);
        motor_set_type(s_motor_type);              // 重新下发配置
        motor_set_encoder_polarity(s_motor_polarity);
        motor_apply_speeds();                      // 目标速度原样恢复
        stalls = 0;
    }
}
```

为什么需要重新下发**配置**而不只是速度：协处理器一旦复位，连 `MOTOR_TYPE`
和编码器极性都会丢，此后它会彻底忽略速度寄存器 —— 光重发速度救不回来。

> ⚠️ 这里踩过一个自己造的坑：最初写成 `motor_stop()` + 重发，但 `motor_stop()`
> 会把目标速度清零，重发的就变成"停"，结果小车会在转弯途中莫名其妙停住。
> 日志里 `drive watchdog` 出现后紧接着 `car stop` 就是这个 bug。

## 四、附带完成：车头灯（避障灯）语音开关

用户要求把「开灯/关灯」接到车头那颗避障灯上。

官方各小车例程只调用 `led_init()` 却从不点灯，图纸也查不到接线；而移植版
`config.h` 里 GPIO2 已经给了 LCD 的 CS，所以官方示例里的 "LED1 = GPIO2" 不可用。
**与其猜，写了个"找灯"程序**：逐个候选引脚（GPIO1 + 5 个 XL9555 扩展 IO）
各给 2 秒高/低电平，让用户观察。

结果：**灯在 XL9555 的 P0.0 上**（官方原理图命名为 `CAMERA_LED_IO`），
极性实测为**高电平点亮**（与官方 LED0/LED1 的"低电平点亮"相反）。

```c
#define XL9555_CAMERA_LED_PIN   0
#define CAMERA_LED_ACTIVE_LOW   0    // 实测高电平点亮
```

## 五、另一个设计错误：「停下」被唤醒门挡住了

用户反馈：**"停下不是很灵，我说了很多遍屏幕也有显示，但是不能停下"**。

看起来像识别问题，其实是**我自己的设计错误**，而且症状特别有欺骗性：

```cpp
ShowHeard(cmd_id, prob);              // ← 屏幕在这里显示"听到: 停下"
if (cmd_id == 1) { OpenCommandWindow(20); }        // 唤醒词开门
else if (!CommandWindowOpen()) {
    ESP_LOGI(TAG, "cmd %d ignored (wake word was not said)");  // ← 命令在这里被丢弃
}
```

**"屏幕显示听到"发生在门检查之前。** 所以用户看到屏幕上明明写着"听到: 停下"，
命令却已经被静默丢弃了 —— 表现完全像"识别不准"，实际是**唤醒门**。

复现条件很明确：车跑起来 20 秒后（唤醒窗口过期），再说「停下」就无效。

**这是安全设计上的错误：急停命令绝不能被任何门挡住。**

修复：

```cpp
const bool is_stop_cmd  = (cmd_id == 8);
const bool is_light_cmd = (cmd_id == 2 || cmd_id == 3);

// 停下:     跳过唤醒门 + 跳过能量门 —— 永远执行(误停是安全方向)
// 开灯/关灯: 跳过唤醒门(只动一颗灯, 不必先唤醒), 仍过能量门滤噪声
// 运动命令:  仍然要求唤醒门 + 能量门
else if (!is_stop_cmd && !is_light_cmd && !CommandWindowOpen()) {
    // 而且现在会在屏幕上直接告诉用户原因, 不再是"显示了却没反应"
    display->ShowNotification("请先说: 你好小车", 1500);
}
```

修复后的门禁规则（一句话：**门禁只管"会不会让车动起来"**）：

| 命令 | 唤醒门 | 能量门 | 理由 |
|---|---|---|---|
| 停下 | 不受限 | 不受限 | 急停必须永远可靠；误停是安全方向 |
| 开灯/关灯 | 不受限 | 不受限 | 只动一颗灯；"说了没反应"比"灯闪一下"更糟 |
| 前进/后退/左转/右转 | 要求 | 要求 | 防止凭空一句话就让小车跑起来 |

实测验证（`_capture.txt`）：

```
[36.5] 前进 → ACTION: forward → wheels TURNED (dL=2833 dR=2764)
[72.3] 停下 → ACTION: stop        ← 相隔 35.8 秒, 唤醒窗口早就过期, 一次生效
```

### 从这里学到的一条通用原则

> **"做了但没生效"和"根本没做"必须在用户界面上区分开。**
> 状态显示（"听到: xx"）表示的是**识别层**的结果，不是**执行层**的结果。
> 只要这两层在界面上长得一样，用户永远无法判断是识别问题还是逻辑问题 ——
> 这次就是靠一行 `cmd 8 ignored (wake word was not said)` 的日志才定位到。

## 六、转向闭环调试：日志说 90 度，眼睛看到 150 度

用户要求把「左转/右转」从"一直原地转"改成"转固定 90 度就停"。为此启用了板载
IMU（QMI8658，此前完全闲置），用 100Hz 积分陀螺 Z 轴得到航向，做闭环转向。

调试过程中连续踩了四个坑，每个都是靠"日志 vs 观察"的对比才定位：

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 静止 8 秒航向漂 109 度 | 开机零偏标定只取前 200 样本均值，被陀螺刚使能的瞬态带偏 | 丢弃前 300ms + 3σ 剔除离群点 |
| 2 | 漂移改不掉（自校正失效） | 零偏自跟踪用"扣掉零偏后的角速度 < 3dps"判断静止 —— 零偏本身偏了 12dps 时永远进不了该分支，**自校正把自己锁死了** | 静止判据改用**原始值** |
| 3 | 说左转却转 180 度，且左右不对称 | 陀螺符号默认值照抄了官方固件的 `IMU_Z_SIGN=-1`，本板子实际是 `+1` → 每次上电第一次转向朝反方向判 → 400ms 后自检翻转 → **再从头转一遍**，累计多转近百 | 默认值按实测改 `+1`；翻转时用"已转过的量"做补偿 |
| 4 | **日志说精确停在 90.0 度，眼睛看到 150 度** | **惯性滑转**：闭环在"陀螺读数到位"那一刻就停车，但车身有角动量，停车后又滑了 60 度；而日志记录的是**停车瞬间**的角度 | 提前减速 + 停稳后重测 + 小步蠕行精修 |

第 4 个坑的日志证据：

```
W 停车后惯性又滑了 60.4 度 (现航向 144.5, 目标 84.1), 开始精修
转向完成: 目标 90 度, 停车瞬间 90.0 度, 停稳 87.2 度 (惯性 60.4), 残差 2.8 度
```

**90.0 + 60.4 ≈ 150 度 —— 与用户肉眼观察完全一致。**

### 这里最值得写进答辩的一条方法论

> **当"测量值"和"观测值"不符时，先怀疑"测量的是什么时刻、什么对象"，
> 而不是先怀疑标定系数。**

我前两轮都去改标定（先猜量程错、再猜符号错），改了两遍都没用 —— 因为闭环**每一次**
都精确停在 90 度，问题根本不在闭环里，而在"停车之后"。后来把"停车瞬间"和"停稳之后"
拆成两次测量，问题一眼就暴露了。

### 附带发现的两个工程问题

- **控制环不能用带副作用的接口**：转向循环每 10ms 调一次 `motor_set_wheel_speeds()`，
  而那个函数每次都会读电池 + 打日志 + **新建一个任务**。一次 0.3 秒的转向因此刷了
  20 多行日志、建了 20 个任务、在共享 I²C 总线上多做了 40 次事务。为此增加了
  `motor_set_wheel_speeds_quiet()` 专供控制环使用。
- **共享 I²C 上的乱码读数会直接变成假转角**：一次错误的 2000dps 采样 × 10ms 就是
  20 度的假转动，静止漂移 2.3°/s 正是这么来的。现在加了 800dps 的合理性上限。

## 七、避障联锁的两个坑：拦错了对象、阈值自相矛盾

加了车头超声波之后连着踩了两个坑，都属于"规则写得太粗"：

### 坑 1：避障把"转向"也拦住了

第一版是"只要在运动 + 前方近 → 停车"，于是**前方 30cm 内有东西时喊「左转」，
避障任务 50ms 内就把转向掐断** —— 用户的原话是"转弯前如果前面有障碍物会转不动"。

但**原地转向根本不改变车的位置，不可能撞上前方的东西**。按运动类型区分才对：

| 运动 | 前方传感器 | 理由 |
|---|---|---|
| 向前开 | 约束 | 会撞上前方的东西 |
| 原地转向 | **不约束** | 位置不变，撞不到前方 |
| 倒车 | **不约束** | 前方传感器管不着车尾 |

### 坑 2："拒绝启动的距离"必须大于"行驶中停车的距离"

原本把"拒绝前进的阈值"设得比"停车阈值"小，就会出现：

```
停在 18cm(触发停车) → 用户又说"前进" → 18cm ≥ 拒绝阈值, 允许 → 车一动
→ 立刻又满足停车条件 → 停 → 再动 → 再停  ← 原地一抽一抽地抖
```

修正为 `拒绝启动距离(20cm) > 行驶中停车距离(18cm)`，两个规则才不会互相打架。

### 另外：刹车距离不能靠"感觉"

第一版把停车阈值定在 20cm，用户反馈"会碰到障碍停下，但惯性会撞上去"。
按公式算就明白了：

```
需要的刹车距离 = 检测延迟 × 速度 + 停车响应 × 速度 + 惯性滑行
              = 0.1s × 87cm/s + ... ≈ 25cm 以上
```

而当时只给了 20cm，**必然撞**。改成"速度 25→15 + 70cm 起提前减速到 8 + 18cm 停车"之后
（到 18cm 时车速已只有约 28cm/s），实测完全能停住。

> **经验：安全阈值不能用"看起来够远"来定，要按"检测延迟 + 响应延迟 + 滑行距离"倒推。**

## 八、可复用的经验（写进答辩也很加分）

1. **"日志显示成功"不等于"硬件真的执行了"。**
   所有下发动作的日志都必须打在**动作之后**，并带上返回值。
2. **给执行类动作加"结果核对"**（读编码器/传感器回值），
   否则软件永远无法区分"指令没到"和"到了但没生效"。
3. **区分"没输出"和"带不动"，量带载电压。**
   失败时电压不掉 → 对方根本没输出；电压塌下去 → 供电/负载问题。
   这一个测量就把排查范围砍掉一半。
4. **一次测试一种变量，且必须重复。**
   我们差点把"22 不能驱动、25 可以"当成结论 —— 直到把同一速度重复 3 次，
   才发现是随机故障，之前的速度扫描只是碰运气。
5. **出现"不可能的数值"要立刻当线索**：4700 万脉冲、电池 0 mV 这种读数，
   直接指向通信层而不是算法层。
6. **降速是通信不稳的万能第一步**：100 kHz 是 I²C 标准模式，
   控制类指令对带宽没有要求，牺牲带宽换稳定永远是划算的。
