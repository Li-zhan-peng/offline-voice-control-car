# 算法创新实验记录：离线语音命令词的模型选型与判决规则优化

> 工程：`<project>`（ESP32-S3 幻尔小车 + 小智离线固件）
> 评测工具：`<repo>\_bench_tts.py` 等
> 一句话：**先把"评测"做成可复现的实验，再拿它去选模型和改判决算法。**

---

## 一、研究问题

小车的离线语音控制跑在 ESP-SR 的 MultiNet 命令词模型上。要回答三个问题：

1. **选哪个模型？** mn5q8 / mn6 / mn7 三代中文命令词模型，体积差 1.6 MB，
   在"我们的口令集 + 真实麦克风 + 电机噪声"条件下谁更准、谁更快？
2. **门限怎么定？** 固件里只有一个全局触发门限（0.15）。它对 7 条口令一视同仁，
   明显不合理 —— 实测中「开灯」能到 0.85，「关灯」常年在 0.16 徘徊。
3. **听不懂和听错，哪个更不能接受？** 小车场景里，把「后退」听成「前进」是灾难，
   而"没反应"只是再喊一次。所以判决规则应该**宁可拒识，不可误动**。

## 二、评测平台：为什么不能靠"人来喊几遍"

人工喊口令，每次音量、语速、距离、情绪都不同，三个模型之间根本无法公平比较。
手工"喊 20 次统计成功率"还有个更隐蔽的坑：**两次播放之间隔几秒，Windows 音频设备
会进入低功耗，下一句的开头被吃掉一截**。我们真踩到了 —— 同一批 WAV 分开播放时
mn5q8 只有 38%~48%，改成一整条轨道连播后是 67%~71%，差的全是设备唤醒伪影。

最终方案（`_bench_tts.py`）：

```
PC 端生成固定 WAV(TTS 固定音色) → 归一化到同一峰值 → 拼成一条长测试轨
        ↓ 一次性连续播放（设备全程醒着，试验间隔完全一致）
小车麦克风拾音 → MultiNet 识别 → 串口打印 LOCAL CMD + MNPOST(后验)
        ↓ 后台线程给每行串口日志打 PC 单调时钟时间戳
用"播放结束时刻 - 轨道总时长"把两边时钟对齐 → 逐次试验对号入座
```

对齐用**结束点**而不是开始点：`PlaySound` 是阻塞的，结束时刻很准；开始时刻含
音频设备打开延迟（实测 350~400 ms），用它会让延迟普遍虚高 350 ms 左右。

### 轨道布局（`layout=block`，用于模型对比）

```
[3s 引导] [口令][3s 静音] [口令][3s 静音] ... x56  [唤醒词 x5] [20s 纯静音]
```

- 只念口令、**不念唤醒词** → 固件的"唤醒门"始终关着 → 电机一次都不转
  → 识别结果不被电机噪声污染（模型对比要的是干净条件）
- 结束的 20 s 纯静音用来统计**凭空误触发**

### 指标定义

| 指标 | 定义 |
|---|---|
| 识别率 | 该次口令被正确识别 / 总次数 |
| 响应延迟 | 词尾（WAV 中最后一个有效采样点）→ 板子打出识别日志 |
| 静音误触发 | 纯静音段里凭空冒出的识别次数 |
| 误驱动 | 实际触发了电机动作的次数（block 布局应为 0） |

## 三、模型对比数据

测试条件：`track_std8`（56 次 = 7 条口令 × 8 轮，随机顺序固定 seed），
TTS 音色 `Microsoft Huihui`，音频归一化到峰值 30000，小车架起、唤醒门关闭、电机不转。

| 模型 | srmodels.bin | 识别的模型名 | 识别率 | 响应延迟 | 静音误触发 | 误驱动 |
|---|---|---|---|---|---|---|
| mn5q8_cn | 2494857 B (2.38 MB) | mn5q8_cn | **62.5%** (35/56) | **350 ms** | 0 | 0 |
| mn6_cn | 3994697 B (3.81 MB) | mn6_cn | **92.9%** (52/56) | 510 ms | 0 | 2 |
| mn7_cn | 2972389 B (2.83 MB) | mn7_cn | **92.9%** (52/56) | 507 ms | 0 | 0 |

分口令识别率：

| 口令 | mn5q8 | mn6 | mn7 |
|---|---|---|---|
| 开灯 | 7/8 (88%) | 8/8 (100%) | 8/8 (100%) |
| 关灯 | 8/8 (100%) | 8/8 (100%) | 7/8 (88%) |
| 前进 | **1/8 (12%)** | 7/8 (88%) | 6/8 (75%) |
| 后退 | 7/8 (88%) | 8/8 (100%) | 8/8 (100%) |
| 左转 | 6/8 (75%) | 7/8 (88%) | 7/8 (88%) |
| 右转 | 5/8 (62%) | 8/8 (100%) | 8/8 (100%) |
| 停下 | **1/8 (12%)** | 6/8 (75%) | 8/8 (100%) |

**结论**

- **mn5q8 直接淘汰**：前进、停下只有 12%，小车会"叫不动 / 喊不停"，安全隐患。
- **mn6 与 mn7 精度相同（都是 52/56）、延迟相同（510 vs 507 ms）**，
  但 **mn7 的模型小 1.02 MB（↓26%）**，为 16 MB Flash 的板子省出空间。
  → **选 mn7_cn**。
- 三个模型的静音误触发都是 0，说明"误触发"不是模型问题，而是**固件只有一个全局门限**
  这件事的问题（见第四节）。

**唤醒词单独说明**：在 block 轨道里 5 条唤醒词背靠背连放（间隔 2 秒）会明显低估唤醒率
（mn5q8 60% / mn6 40% / mn7 40%）；换成接近真实节奏的 6 秒间隔单独测，
**mn7 唤醒率 80%（4/5）**。这个协议伪影本身也写进了第六节的踩坑表。

## 四、算法创新：把"一个门限"换成"召回层 + 精度层"

### 4.1 先看模型给了什么信息

ESP-SR 触发时会返回 top-5 候选和后验概率，而原固件只用 `prob[0]`、丢掉亚军：

```c
typedef struct {
    int num;                                // 候选数
    int command_id[ESP_MN_RESULT_MAX_NUM];  // 候选命令 id
    float prob[ESP_MN_RESULT_MAX_NUM];      // 对应后验概率
} esp_mn_results_t;
```

### 4.2 第一版方案（后验规则）——被数据否定了

想法很自然：`score = prob + bias[命令]`，再用 `tau`（绝对置信度）和
`margin`（top1-top2 边际）做拒识。于是把全局门限压到 **0.05 当召回层**，
把每次触发的完整后验打到串口，离线分析（`_analyze_rules.py`）。

实测结果（mn7_cn，56 次口令 + 全程约 290 秒无口令时段）：

| 观察 | 数值 |
|---|---|
| 召回率（门限 0.05） | **100% (56/56)**，比门限 0.15 的 92.9% 高 7.1 个百分点 |
| 判错 | **0 次**（top-1 全对，没有混淆） |
| 真口令的 top-1 后验 | 平均 0.178，**最低 0.051** |
| 噪声凭空触发的后验 | 平均 0.081，**最高 0.141** |
| 边际（top1−top2） | 所有检测 `num=1`，**根本不存在亚军** |

**结论：后验概率分不开"真口令"和"噪声触发"——真口令最低 0.051 比噪声最高 0.141 还低，
两者完全重叠；边际特征更是完全不存在。** 这一版规则只能靠调门限硬顶，
而调门限必然"召回上去了误触发也上去"。

### 4.3 第二版方案（能量证据）——换成"像不像人在说话"

既然模型输出分不开，就引入模型之外的特征：**检测发生的那一刻，输入信号里到底有没有语音能量。**

- 慢速平均 RMS（时间常数约 6 秒）→ 环境噪声底；最近约 1 秒的峰值 RMS → 语音能量
- 特征值 = 两者之比 `ratio`；真口令说完时比值高，噪声触发时接近 1

实测（同一批数据）：

| 类别 | 样本 | 平均 | 最低 | 最高 |
|---|---|---|---|---|
| 真口令 | 54 | **5.32** | **1.94** | 9.94 |
| 噪声凭空触发 | 7 | **1.14** | 0.42 | **2.54** |

门限扫描：

| 能量门 K | 真口令保留 | 噪声挡掉 |
|---|---|---|
| 1.0 | 100% | 43% |
| **1.5** | **100%** | **86%** |
| 2.0 | 98% | 86% |
| 3.0 | 89% | 100% |
| 5.0 | 54% | 100% |

按小车场景的代价函数 `代价 = 3 × 误动 + 1 × 漏检`，**K=1.5 最优**（代价 3，优于 K=2.0 的 4、
K=3.0 的 6）。

### 4.4 组合后的系统

```
全局触发门限 0.05        ← 召回层：把该报的都报出来（召回 92.9% → 100%）
   ↓
设备端判决规则            ← 精度层：
   score[i] = prob[i] + bias[i]      (后验偏置，本数据里 bias 全 0)
   接受需同时满足：
     score_max >= tau[id]             (绝对置信度，本数据未启用)
     score_max - score_2nd >= margin  (边际，本数据未启用)
     ratio >= 1.5                     (能量门 ↔ 实测挡掉 86% 噪声误触发)
   否则拒识：屏幕提示"没听清,请再说一遍"，不动电机
   ↓
唤醒词也过能量门 —— 凭空唤醒会开出 20 秒命令窗，比凭空报一条口令更危险
```

代价：每 32 ms 一次乘加（512 点 RMS），**零额外内存、不增加识别延迟**。

### 4.5 部署后验证

把规则烧进固件后，用**同一条 std8 轨道**重测（`bench_mn7_deployed.txt`）：

| 配置 | 命令词召回 | 无口令时段误触发 | 实际误动 |
|---|---|---|---|
| 门限 0.15（原固件） | 92.9% (52/56) | 0 | 0 |
| 门限 0.05（只降门限） | 100% (56/56) | 7 次 | 1 次（会真的动） |
| **门限 0.05 + 能量门 K=1.5（本方案）** | **100% (56/56)** | **1 次，且能量比 0.57 远低于门限，被挡掉** | **0** |

同一次验证里（独立一次运行，不是调参用的那批数据）：

| 类别 | 样本 | 能量比 最低 | 能量比 平均 |
|---|---|---|---|
| 真口令 | 56 | **2.66** | 6.95 |
| 噪声凭空触发 | 1 | **0.57** | 0.57 |

**两者完全不重叠**，K=1.5 时真口令 100% 保留、噪声 100% 挡掉。

再用 **flow 轨道**测真实使用流程（唤醒词 + 1.2 秒后说口令 + 电机会真的转起来，
每次试验 10 秒节奏）：

| 指标 | 结果 |
|---|---|
| 指令识别率 | **100% (21/21)** |
| 唤醒成功率 | **100% (21/21)** |
| **完整流程（唤醒→口令一次说对）** | **100% (21/21)** |
| 响应延迟 | 516 ms（平均） |
| 静音误触发 | 0 |
| 凭空误唤醒 | 0 |
| 实际执行动作 | 36 次（21 条口令 + 15 次清理"停下"），被规则拒识 0 次 |

> 顺带解决了上一节那个"唤醒率只有 40%"的疑点：flow 轨道里唤醒词后面 1.2 秒紧跟口令，
> 唤醒率就是 100%；block 轨道里 5 条唤醒词以 3.83 秒间隔背靠背连放才是 40%。
> **说明那个低唤醒率是评测协议造成的，不是模型能力。**

### 4.6 一句话总结创新点

> 我们先用可复现的自动评测台把三个模型比清楚（选 mn7，精度与 mn6 相同但模型小 26%），
> 再用实测数据证明"后验概率无法区分真口令与噪声误触发"（真口令最低 0.051 < 噪声最高 0.141），
> 于是把判决拆成**召回层**（把 ESP-SR 门限压到 0.05，召回 92.9%→100%）
> 和**精度层**（设备端语音能量证据 `最近1秒峰值RMS / 环境噪声底 ≥ 1.5`，挡掉 86%~100% 的噪声误触发），
> 最终真实流程成功率达到 100%，且零误触发、零误动，规则本身每 32 ms 只多一次乘加。


| 层 | 手段 | 这一层失效时 |
|---|---|---|

   不必再喊唤醒词；一停下窗口立刻关闭，下次要动需重新唤醒。
10. **能量门用真人数据重标定**：台式标定用 TTS 近场音（真口令 ≥1.94），门限取 1.5；
    真人实测发现说话更轻时会掉到 1.39/1.25 被误挡。回头查噪声分布
    0.42/0.75/0.95/1.06/1.08/1.15/2.54 —— 除一个离群点外全在 1.15 以下，
    于是门限降到 **1.2**：挡噪声能力不变，真口令通过率提高。

**两个已知的小尾巴**

- 能量门偶发误拒：真人测试中出现过 `RULE: wake REJECTED by energy gate (ratio=1.25)`，

## 附：已知坑（写进论文/答辩也算工作量）

| 现象 | 真实原因 | 处理 |
|---|---|---|
| 分句播放时识别率忽高忽低 | 音频设备低功耗，句首被吞 | 改单条轨道连续播放 |
| 延迟 800 ms 偏大 | 用播放**开始**时刻对齐，含设备打开延迟 | 改用**结束**时刻对齐 |
| 前几次试验必失败 | 板子还没加载完模型就开始测 | 等串口打出模型名/命令表再开测 |
| 唤醒词连测 5 次只中 1~2 次 | 5 条唤醒词背靠背连放，与真实间隔不符 | 唤醒单独做一轮长间隔测试，或用 flow 轨道的真实配对 |
| 识别率与"感觉"不符 | 电机噪声盖住口令 | 模型对比时小车架起、唤醒门关闭；真实流程另测 |
| 编译突然报 `UnicodeDecodeError: 'gbk' codec can't decode byte 0xa0` | PowerShell 5.1 的 `Get-Content` 默认按 GBK 读、`Set-Content -Encoding UTF8` 写回，把 sdkconfig 里 UTF-8 的中文（`CONFIG_CUSTOM_WAKE_WORD_DISPLAY="你好小车"`）改成了坏字节；esp-sr 的 `movemodel.py` 又用系统默认编码读它 | 一律用 `_set_cfg.py`(Python, 显式 UTF-8) 改 sdkconfig；出问题就 `python _set_cfg.py sanitize` |
| 烧录失败但脚本继续跑，把旧固件当成新模型测 | 脚本没检查返回值 | 评测加 `--expect-model`，板子自报模型不符就直接中止 |
